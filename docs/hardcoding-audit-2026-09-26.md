# Hardcoding audit — 26 September 2026

Investigation only. Reviewed checkout at `1ef8189`; implementation and Ticket 14 remain paused. No provider calls, service restarts, credential changes, or production-code changes were made for this audit. The pre-existing uncommitted cart test changes and unrelated proposal files were preserved.

## Finding

The application calls a real LLM in live session mode, but its decisions pass through a substantial handwritten language interpreter disguised as validation. That interpreter can reject, replace, or augment the model's meaning. This is broader than a spelling bug. Separately, action planning, recommendation selection, and explanation text are predominantly deterministic.

My earlier statement that the agent “does not hardcode Arabic cart phrases” was inaccurate. The newest handoff and checkpoint describe the retry change but fail to acknowledge the existing lexical gates. Adding reconsideration did not remove those gates.

## Scope and method

Inventoried the Agent, model adapters, Bridge, Panel, Controlled Storefront, shared protocol fixtures, evaluation harness, Storefront Definition, and project plans. Traced live versus scripted callers; inspected language matching, decision rewrites, target selection, recommendation ranking, prompts, schemas, and execution safeguards. Reviewed recent Git history for the cart rules. Ran small local probes against the actual validators with supplied schema-valid intents. This is an architectural and behavioral audit, not an exhaustive security review or a fresh full-suite acceptance run.

The probes establish what application code does even when supplied a sensible structured decision. They do not establish what the live model returned in the historical screenshots. No live model accuracy claims follow from them.

## Decisions outside the LLM

**Context is insufficient for the intended role.** `agent/app.py:158` calls interpretation with message, Storefront Definition, resolved state and pending clarification. `build_intent_request` does not accept the current Snapshot. New-task resolved state contains the current text, limited previous destination/suggestions, and subsequent clarification history—not current cart lines, selected variants, or full conversation. The application stores the Snapshot, but uses it later for deterministic planning. The LLM therefore cannot reliably select among actual cart lines from information it never receives.

**Action planning is deterministic.** Despite the class name, `ScriptedPlanner.plan_intent` (`agent/planner.py:219`) is used for live model intents too. It maps intent to known navigation/filter/spotlight workflows. Cart code chooses controls and computes absolute quantities. There is no general live per-step LLM action loop here. Deterministic execution of a validated operation is useful; claiming this is already a general LLM browser planner is inaccurate.

**Recommendations are deterministic after interpretation.** `agent/catalogue.py:395` checks facts and chooses up to three results. Ordinary ordering defaults to product ID unless price/newest is selected. Styling uses preferred colors or the fixed neutral palette at line 110, then color ranking/diversity and mismatch-count thresholds. Reasons are templates (`:166`, `:331`), including neutral-color advice. Thus “best recommendation” is not a model comparison of the retrieved products. Fact verification should remain; ranking and advice need an explicit design decision about the LLM's role.

**Chat text is mostly templated.** `trusted_clarification` (`intent_pipeline.py:1273`), session summaries, action narration, and catalogue reasons use predefined text. The schema has no general conversational response/explanation field. This helps explain repetitive and generic messages; adding a provider alone does not change it. Structured action validation need not prohibit a separate grounded explanation.

**Controlled-store assumptions are embedded in execution.** `cart.py:143` and `:200` use known form routes and Arabic control names such as المقاس, اللون, الكمية, and derive input labels by replacing تحديث الكمية. `sessions.py:62` parses an Arabic product-count heading; `:1175` recognizes cart success through exact known status strings. `planner.py:306` assumes orders are inside account and checkout inside cart. Bridge guarded-action classification uses known mutation routes (`bridge/src/actions.ts:169`). These are local-store adapter assumptions, not shopper-language understanding. They fit a controlled MVP but block arbitrary-store generalization and can cause fragility after UI copy changes.

## Scripted paths and evaluation

- `scripted_cart_intent` (`cart.py:257`), `scripted_mutation_intent` (`confirmation.py:156`), and `ScriptedPlanner.plan_with_intent` / `plan_answer` contain explicit command grammars. The session message route selects these only when provider is `scripted` (`app.py:281`). I found no automatic switch to this parser on a live provider failure.
- The legacy `/step` endpoint (`app.py:253`) always calls the scripted planner, regardless of provider. The current Panel uses `/sessions/{id}/messages` (`panel/src/main.ts:92`), not `/step`. This endpoint should be isolated as demo/test functionality or made consistent; its behavior should not be advertised as live-model planning.
- `ScriptedLLMClient` returns supplied chunks (`agent/llm/contract.py:57`). Tests can run the real HTTP/session/validation path while still supplying ideal model output. That is useful execution coverage, not evidence that the model handles arbitrary speech.
- `eval/services.py:64` selects scripted mode for ordinary browser evaluation. Separate live evaluation exists. Previously citing hundreds of passing tests as reassurance about natural-language reliability overstated what those tests measure. Some tests also enforce the lexical gates, so passing them can preserve the problematic design.
- Provider adapters translate schema/messages and handle transport, output format, quota and retries. The audit found no additional shopper-command parser there. Speech transcription sends recorded audio to a model and fills editable text; the downstream text interpreter still imposes the rules above.
- Panel and store scripts handle UI events, display copy, forms, cart state and ordinary catalogue filtering. I found no second shopper-command parser in those components. Store catalogue records, prices and supported options are expected application data, not evidence that product conversations are secretly canned.

## Safeguards to retain

Same-origin navigation and message-origin checks; exclusion of sensitive values; known live target IDs/options; current-state checks; single-use confirmation bound to the exact guarded mutation; duplicate/stale-action rejection; truthful outcome verification; uncertain-mutation recovery without replay; quantity bounds; exact money arithmetic; cancellation; provider spending limits.

These enforce executable capabilities and state. They do not need to retranslate the shopper's sentence. Exact selection of a displayed confirmation or product-choice button is also legitimate structured input. Matching user prose against a synonym table is a different responsibility.

Schema validation remains necessary, but the schema also encodes current scope limits: one intent at a time, restricted operations/destinations, no general negative-feature constraints, and product IDs only for opening prior recommendations. Unsupported or ambiguous requests need an honest response; removing regex alone will not add missing capabilities.

## Why this accumulated

The original intent was to prevent model-invented quantities, dropped requirements, wrong products and unauthorized mutations. The implementation turned “validate a safe operation against real state” into “independently interpret the sentence using keyword rules.” Later manual failures were patched with more phrases and exceptions instead of correcting that responsibility boundary.

Git history corroborates that progression: cart cue gates were present in `afc6983`; `5e57d8e` added written-number recognition; `8bcf765` expanded Egyptian Arabic matching; `1567887` added relative-request handling; `1ef8189` retried rejected drafts while retaining the validators. These are historical implementation choices, not a requirement imposed by the model provider. The original plans also describe LLM intent and a model-driven action loop beyond the filter fast path, while the current domain document narrows the LLM to intent extraction. That divergence needs an explicit decision.

I should have surfaced this design conflict earlier. The anti-hallucination goal was valid; treating handwritten language rules as reliable semantic evidence, then citing test totals as broad assurance, was not.

## Recommended correction order — not implemented

1. Establish the model decision contract with current cart/product/variant IDs, selected values, useful conversation context and explicit constraints including exclusions. Supply bounded, sanitized observed state. Keep canonical values separate from language aliases.
2. Replace live lexical approval/rewrite gates with LLM interpretation and referent selection. Deterministically validate referenced IDs, supported operations/options and numeric/state constraints. Treat genuine unresolved ambiguity explicitly. Do not replace this with a larger regex list or trust a model merely declaring itself confident.
3. Preserve bound confirmation and state-based execution safeguards. Deterministic arithmetic can compute “current quantity + model-selected delta”; deterministic code should not decide what the sentence meant.
4. Decide and document how much product ranking and grounded explanation the LLM owns. Keep catalogue fact checking and execute only validated operations. Isolate scripted parsers and retire or clearly restrict `/step`.
5. Evaluate a small held-out set of realistic multi-turn conversations, typos, negation, pronouns, variant ambiguity and multi-line carts. Record raw model decision, boundary verdict, executed target and resulting state separately. Retain safety/execution regressions; stop treating scripted language fixtures as live-language acceptance.
6. Correct the handoff/checkpoint claims when the revised design is agreed. Resume Ticket 14 after this boundary is repaired and manually accepted.

No fixes are claimed by this report. In particular, the historical post-add stall and every screenshot have not been re-diagnosed end to end in this audit.
